## 1. 서론

### 1.1 목적

본 문서는 "기능 중심 차량 컨피규레이터"의 요구사항을 정의한다. 팀원 2명은 Unity 설계, 구현, 테스트, 발표 준비 과정에서 본 문서를 기준으로 삼는다.

### 1.2 범위

| 항목 | 내용 |
|---|---|
| 제품 이름 | 기능 중심 차량 컨피규레이터 (가제) |
| 대상 사용자 | 고급 선택 옵션 구매를 고민하는 차량 구매 예정자, 발표·시연 관람자 |
| 제품이 하는 일 | 차체 색상, 트림, 휠을 실시간 미리보기로 보여준다. 주행 기능 2종(나이트 비전, 후륜 조향)과 주차 기능 2종(주차장 연동 발렛, 스마트키 원격 주차)의 선택 전후 차이를 분할 화면 시나리오로 보여준다. 모든 화면 전환은 로딩 없이 하나의 실행 화면 안에서 이루어진다. |
| 제품이 하지 않는 일 | 가격 계산, 주문·결제, 실차 데이터 연동, 네트워크 기능, 사용자 직접 운전 게임 |
| 제품의 가치와 목표 | 이름만으로 이해하기 어려운 고급 옵션을 "선택 안 함 vs 선택함" 비교로 보여주어 구매 판단을 돕는다. 2026.10.14 발표 시연을 목표로 한다. |

### 1.5 작성 규칙

모든 요구사항은 한 문장에 하나의 내용만 담는다.

| 표현 | 의미 | 우선순위 |
|---|---|---|
| ~해야 한다 | 반드시 구현하는 필수 요구사항 | Must |
| ~하는 것이 좋다 | 일정에 따라 미룰 수 있는 요구사항 | Should |
| ~할 수 있다 | 여유가 있을 때 구현하는 선택 요구사항 | Could |

| 구분 | ID 형식 | 예 |
|---|---|---|
| 기능 요구사항 | FR-번호 | FR-01 |
| 비기능 요구사항 | NFR-번호 | NFR-01 |
| 화면 | UI-번호 | UI-01 |
| 테스트 케이스 | TC-번호 | TC-01 |

"대략", "적절히", "빠르게", "등" 같은 모호한 표현은 쓰지 않고 측정 가능한 숫자와 조건으로 기술한다. 본 문서의 거리·시간 수치는 초기 설정값이며, 변경 시 개정 이력에 기록한다. 요구사항 ID는 삭제·추가 시에도 기존 번호를 바꾸지 않고 새 번호를 뒤에 붙인다.

### 1.6 문서 구성

2장은 제품 전체를 이해하기 위한 개요이다. 3~6장은 구현에 필요한 상세 요구사항이며, 주행 기능은 김예은, 주차 기능은 강유나, 영역 전환은 두 사람이 함께 본다. 7장은 요구사항의 검증 방법을 정의한다.

## 2. 제품 개요

### 2.1 제품 관점

본 제품은 외부 시스템과 연동하지 않는 독립 실행 프로그램이다. 주차장 연동 발렛의 "관제 시스템"도 제품 내부에서 시뮬레이션한다.

```
사용자 → 키보드·마우스 → 기능 중심 차량 컨피규레이터 (Windows 실행 파일) → 모니터 화면
```

**내부 구성**

제품은 실행 중 씬을 다시 로드하지 않는다. 앱 시작 시 MainScene과 영역 씬 3개를 한 번에 불러오고, 이후에는 영역을 켜고 끄는 방식으로 화면을 전환한다.

```
MainScene (항상 활성)
 ├ ModeManager      : 영역·카메라·조명 전환
 ├ CarConfig        : 선택 옵션 보관
 └ 공통 UI Canvas, EventSystem, AudioListener

ConfiguratorArea.unity (Additive) : 쇼룸, 밝은 조명         ← 공동
DrivingArea.unity      (Additive) : 야간 도로 코스 2벌      ← 김예은
ParkingArea.unity      (Additive) : 주차장 2벌              ← 강유나
```

**유사 제품 비교**

| 제품 | 공통점 | 차이점 |
|---|---|---|
| 제조사 웹 컨피규레이터 | 색상·트림·휠을 고르면 차량 외관을 보여준다 | 본 제품은 기능 옵션의 동작을 시나리오로 재현하고 선택 전후를 비교한다 |
| 제조사 기능 소개 영상 | 기능 동작을 시각적으로 보여준다 | 본 제품은 사용자가 고른 외관·기능 조합으로 실행되고, 운전석·버드뷰 시점을 바꿀 수 있다 |

### 2.2 제품 기능

제품은 외관 선택 → 기능 선택 → 시나리오 비교의 3단계로 진행하며, 단계 사이는 로딩 없이 영역 전환으로 이동한다.

- 외관 선택: 차체 색상, 트림, 휠을 고르면 차량에 즉시 반영
- 기능 선택: 주행 기능 2종, 주차 기능 2종 선택 후 \[주행 시작\] 또는 \[주차 시작\]
- 주행 시나리오 (김예은): 야간 외곽 도로에서 나이트 비전, 막다른 골목에서 후륜 조향
- 주차 시나리오 (강유나): 다수 차량 주차장에서 주차장 연동 발렛, 좁은 주차면에서 스마트키 원격 주차
- 공통: 분할 화면 비교, 운전석 ↔ 버드뷰 전환, 영역 전환과 초기화

### 2.3 사용자 특성

| 사용자 유형 | 특성 | 주요 사용 기능 |
|---|---|---|

| 발표 시연자 | 제품 구조를 알고 있다. 제한된 시간 안에 모든 기능을 보여줘야 한다. | 전 기능, 시점 전환, 일시정지 |
| 평가자·면접관 | 기술 구현 근거를 확인한다. | 버드뷰 센서·궤적 시각화, 수치 표시 |

### 2.5 가정 및 의존성

- 시연 PC는 Windows 10 이상이며 독립 그래픽카드를 갖춘다.
- 시연 PC의 메모리는 영역 씬 3개를 동시에 올려둘 수 있다.
- 시나리오 차량은 사용자가 운전하지 않고 정해진 경로를 자동 주행한다. 이 가정이 바뀌면 분할 화면 비교(FR-11) 요구사항이 바뀐다.
- 차량 3D 모델은 트림 파츠와 바퀴가 분리된 무료 에셋을 구할 수 있다.
- 영역은 서로의 조명과 카메라에 비치지 않도록 좌표를 떨어뜨려 배치한다. (옵션 선택 영역 X=0, 주행 영역 X=2000, 주차 영역 X=4000 기준)
- 주차 기능의 상세 동작은 강유나 검토 후 확정한다.

## 8. 변경 관리

요구사항 변경은 두 사람이 모두 동의해야 반영한다.

1. 변경을 제안하는 사람은 GitHub Issue에 `변경 요청` 라벨로 대상 ID, 변경 내용, 사유를 적는다.
2. 매일 19:00 마감 회의에서 두 사람이 검토한다.
3. 모두 동의하면 본 문서를 수정하고 개정 이력에 날짜, 변경자, 변경 내용, 변경 사유를 기록한다.
4. 일정 부족으로 기능을 빼야 하면 Could → Should → Must 순서로 보류한다.
5. `MainScene.unity`, `ConfiguratorArea.unity`, 공통 차량 프리팹, `CarConfig.cs`를 수정할 때는 작업 전에 상대에게 알리고, 수정 후 바로 `dev`에 병합한다.

```
  주행 영역 비활성 → 옵션 선택 영역 활성, 활성 씬 = ConfiguratorArea
```

- 영역 배치 좌표 (기준값):

| 영역 | 씬 파일 | 루트 오브젝트 | 배치 X 좌표 | 담당 |
|---|---|---|---|---|
| 옵션 선택 | `ConfiguratorArea.unity` | `ConfiguratorRoot` | 0 | 공동 |
| 주행 | `DrivingArea.unity` | `DrivingRoot` | 2000 (코스 A), 3000 (코스 B) | 김예은 |
| 주차 | `ParkingArea.unity` | `ParkingRoot` | 4000 (주차장 A), 5000 (주차장 B) | 강유나 |

- 후륜 조향 회전 반경 계산(자전거 모델, L = 축거리, δf = 앞바퀴 조향각, δr = 뒷바퀴 조향각, 역위상일 때 δr을 음수로 둔다):

$$
R = \frac{L}{\tan\delta_f - \tan\delta_r}
$$

- 나이트 비전 TTC 계산:

$$
TTC = \frac{d}{v_{rel}}
$$
